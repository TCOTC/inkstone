## 安装形式与数据归属（开发版 ↔ 商店版）

**这一节解决一个会静默丢数据的问题**：`chrome.storage.local` 与 `chrome.storage.sync`
**都按扩展 ID 分区**。ID 变了，数据既没被删、也没报错，只是**再也没有入口能读到**——
界面上看起来就是「划线全没了」。

### ID 是从哪来的

| 安装形式 | ID 来源 | 换目录 / 换机器会变吗 |
| --- | --- | --- |
| 未打包（`chrome://extensions` → 加载已解压的扩展程序） | **加载路径**的 SHA-256 | **会变** |
| 商店安装 | 商店条目首次上传时生成的公钥 | 不变 |
| 任意形式带 `key` 字段 | 该公钥的 SHA-256 | 不变 |

`pnpm verify` 会打印当前产物的 ID（没有 `key` 时按加载路径算），可以用来核对：

```bash
node tools/extension-id.mjs            # 打印 ID 与它是由什么决定的
```

算法来自 Chromium `components/crx_file/id_util.cc`：SHA-256 前 16 字节，十六进制每位
`0..f` 映射成 `a..p`。`tools/extension-id.mjs` 每次运行都先跑一遍官方单测
（`id_util_unittest.cc`）里的五个向量自检，对不上就 `exit 1`。

### 开发版 → 商店版：怎么迁移

**先迁数据，再清旧数据。** 顺序反了就只能靠备份来回倒。

1. **在开发版里导出备份**（偏好设置 → 导出备份）。这份 JSON 里有全部页面、划线与设置，
   `version` 稳定，商店版导入后按 URL 覆盖同页，本地新划的线保留。
2. 装上商店版，**导入那份备份**。数据就完整过去了，与新 ID 无关。
3. 卸载开发版。**Chrome 会连它的 `storage.sync` 一起清掉**——Chromium
   `SyncStorageBackend::DeleteStorage()` 的注释就是「Clear settings when the extension is
   uninstalled」，而且这次清除会经同步链路上传，其它设备上的旧副本也会消失。
   不需要任何额外操作，这正是回答「旧的云端数据怎么清理」的那一句。

如果不想卸载（例如想留一份可回退的开发版）：在开发版的偏好设置里点**「清除云端数据」**。
它只清云端、不动本机，且**不看同步开关**——关掉同步之后才最需要它。

> 已知边界：**另一台设备仍装着开发版并且开着同步**时，它下次写入某页会把那一页再写回
> 云端。要彻底清空，先在所有设备上卸载/关掉旧版。

### 更好的做法：一上来就固定 ID

清旧数据是补救，**固定 ID 才是根治**：开发版与商店版共用一个 ID，数据天然连续，
连迁移都不用做。官方步骤（见 Chrome 文档 *Keep a consistent extension ID*）：

1. 把 `pnpm build` 的 `dist/chrome` 打成 zip；
2. 在开发者后台 **添加新条目** → 上传 zip（**先不要发布**）；
3. **Package** 标签 → **View public key** → 复制 `---BEGIN/END PUBLIC KEY---` 之间的内容，
   去掉换行；
4. 粘进 `src/manifest.json` 的 `"key"` 字段。

之后本地加载的 ID 与商店条目一致。**越早做越好**：这个操作本身会改变开发版 ID，
所以最好在还没积累真实数据时做；已经有了就先走上面的「导出 → 导入」。

固定 ID 还顺带解决一个更隐蔽的坑：**移动或重命名仓库目录**会改变开发版 ID，
`storage.local` 里的划线同样会变成读不到的孤儿数据。现在 `tools/extension-id.mjs`
能把这件事算出来并核对。

### 为什么 `key` 不默认写进清单

因为它的取值取决于商店条目，而这个条目现在还不存在。随手生成一个自己的公钥只能固定
「开发期」的 ID，等商店条目建好之后还得再换一次——换的那一次又把 ID 变了一次。
所以当前状态是：**清单不带 `key`，`pnpm verify` 每次提示这一点**。
等商店条目建好，把它的公钥粘进来即可，`verify` 的提示会自动消失。
